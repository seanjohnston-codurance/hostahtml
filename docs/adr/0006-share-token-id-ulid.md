# ADR-0006: Share token identifier — ULID

Date: 2026-05-13  
Status: Accepted

## Context

**ADR-0005** introduces opaque share tokens as the DynamoDB partition key and as the `{token}` segment in **`GET /t/{token}`**. Tokens must be **unguessable**, **URL-safe**, **unique per upload**, and stable in the URL path without encoding surprises.

We also want **time-sortable** identifiers so logs, support, and future features (e.g. listing, analytics) can order shares roughly by creation time without exposing the S3 object key.

## Decision

Use **ULIDs** (26-character **Crockford base32**) generated by the **[`ulid`](https://www.npmjs.com/package/ulid)** npm package:

- Call **`ulid()`** for each new share at upload time. **`monotonicFactory()`** is reserved for the rare case of many IDs minted in the same millisecond on one host; normal uploads do not require it.
- Store the string returned by the library **as-is** (canonical **uppercase** Crockford) in DynamoDB and embed it in **`/t/{token}`**.
- On **`GET /t/{token}`**, **normalize case** if needed before `GetItem`, and reject strings that are not exactly **26 characters** of valid Crockford base32 with **404** (avoid junk keys hitting DynamoDB).

## Alternatives considered

| Option | Why not chosen for phase 1 |
| ------ | -------------------------- |
| **`randomBytes` + base64url** | Shorter URL; **not** time-sortable without extra metadata. |
| **UUID v4** | Standard and ubiquitous; longer than ULID; not time-sortable. |
| **UUID v7** | Time-sortable; acceptable substitute; team preference for ULID’s fixed width and common tooling in the ecosystem we use. |
| **nanoid** | Shorter; time-ordering not a first-class property of the default id. |
| **Hash of file or S3 key** | **Rejected:** deterministic ids leak “same file” across re-uploads; truncated hashes complicate collision and guessing analysis; no benefit over random when DynamoDB holds the mapping. |

## Consequences

**Positive:**

- Lexicographic order of `token` approximates creation order (helpful for ops and future product).
- 128-bit space with explicit timestamp component; well-tested libraries.

**Negative:**

- **Approximate creation time** (and ordering between shares) is inferable from the id alone. Acceptable for internal Codurance HTML sharing; **revisit** if we need ids that do not leak timing (then prefer v4 or base64url random only—see alternatives above).
- Small **npm dependency** (`ulid`) in the API workspace.

## See also

- **ADR-0005** — DynamoDB share tokens, `GET /t/{token}`, redirect to short-lived presign.
- **ADR-0003** — 7-day policy; token row `expiresAt` stays aligned with object lifetime.

## Reconsider if

- Product forbids **timing leakage** from public ids.
- We standardise on **UUID v7** org-wide and want one less dependency.
- URLs must be **shorter than 26 characters** at the same security margin (then evaluate nanoid or shorter encodings with explicit security review).
