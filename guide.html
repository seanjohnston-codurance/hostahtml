Deploy hostahtml to AWS

A step-by-step guide for Azure developers. Tick each step as you go — progress is saved to this browser.

1 Prerequisites

Install Node.js 20+

Node powers both your TypeScript app and the CDK toolkit.

bash
brew install node@20

No Homebrew? Install it from brew.sh first, or use nvm below.

powershell
winget install OpenJS.NodeJS.LTS
bash
# via fnm (recommended)
curl -fsSL https://fnm.vercel.app/install | bash
fnm install 20 && fnm use 20
Install AWS CLI v2

The AWS CLI is your az. You use it to authenticate, inspect resources, and run CDK commands.

Use the official installer — not brew install awscli. Homebrew pulls in Python 3.14 as a dependency, which has a known conflict with macOS's bundled libexpat and will crash on every aws command.

bash
curl "https://awscli.amazonaws.com/AWSCLIV2.pkg" -o /tmp/AWSCLIV2.pkg
sudo installer -pkg /tmp/AWSCLIV2.pkg -target /

If you already installed via Homebrew and are seeing a Symbol not found: _XML_SetAllocTrackerActivationThreshold error, uninstall it first: brew uninstall awscli, then run the commands above.

Download and run the AWS CLI v2 MSI installer.

bash
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip && sudo ./aws/install
Azure equivalent

This is the AWS version of the az CLI. Same idea — authenticate your terminal and manage cloud resources from the command line. Commands look like aws s3 ls instead of az storage blob list.

Install AWS CDK and ts-node

CDK lets you define AWS infrastructure in TypeScript instead of YAML. ts-node lets CDK run your TypeScript code directly.

bash
npm install -g aws-cdk ts-node
Azure equivalent

CDK is TypeScript-first infrastructure-as-code — similar to Pulumi. You write real code (not YAML), and CDK turns it into CloudFormation templates behind the scenes. Think of it as Pulumi for AWS, or Bicep if you prefer the analogy to a declarative approach — but with actual TypeScript types and IDE autocomplete.

CloudFormation (what CDK generates) is AWS's equivalent of ARM / Bicep. You rarely write CloudFormation directly — CDK does it for you.

Verify your installs
bash
node --version   # v20.x.x or later
aws --version    # aws-cli/2.x.x
cdk --version    # 2.x.x

2 Create CLI Credentials

🏢 Company account — check before creating anything UK Playground is shared. Before creating an IAM user, check IAM → Users to see if one already exists for you, and ask whoever manages your AWS setup how developers are expected to get access. Many companies use IAM Identity Center (SSO) — if that's the case here, the setup is browser-based login rather than access keys (see the collapsible below).
Switch to the UK Playground account in the Console

In the AWS Console, click your account name in the top-right corner. You should see a Switch role option or a list of accounts. Navigate to UK Playground.

Azure equivalent

Same as switching subscriptions in the Azure portal. AWS Organizations groups multiple accounts under one roof; you move between them via Switch Role — equivalent to changing the active subscription.

Create an IAM user for this service

Go to IAM → Users → Create user:

  • User name: hostahtml
  • Leave Provide user access to the AWS Management Console unticked

This covers exactly what CDK needs: CloudFormation, S3, Lambda, API Gateway, the IAM roles CDK creates, and the SSM/ECR/Logs infrastructure CDK bootstrap sets up. The policy is also saved in the repo at infra/iam/hostahtml-deploy-policy.json.

Azure equivalent

An IAM user with access keys = a service principal with a client secret, scoped to a specific app. It's the identity your local CLI uses when deploying this service. CI/CD pipelines use IAM roles via OIDC (already set up in the CDK stack) — this user is only for local cdk deploy runs.

Generate access keys

Click into the hostahtml user → Security credentials tab → Create access key.

  • Select Command Line Interface (CLI) as the use case
  • Click through to the final screen — you'll see an Access key ID and a Secret access key
  • Copy both now — the secret is only shown once
Keep these safe These keys authenticate you to AWS. Don't commit them to git, don't paste them in Slack. Store them in a password manager.
Configure the AWS CLI profile
bash
aws configure --profile hostahtml
  • AWS Access Key ID: the key ID you just copied
  • AWS Secret Access Key: the secret you just copied
  • Default region name: eu-west-1 (or your region)
  • Default output format: json
Verify it works
bash
aws sts get-caller-identity --profile hostahtml

You should see the UK Playground account ID and an ARN ending in user/hostahtml. If you get an error, double-check the keys were copied correctly.

💡 Skip --profile on every command Both aws and cdk respect the AWS_PROFILE environment variable. Use mise to set it automatically whenever you're in this directory:
bash
echo -e '[env]\nAWS_PROFILE = "hostahtml"' > .mise.toml
mise trust
After that, cdk deploy and aws s3 ls work without any --profile flag whenever you're in this directory. The .mise.toml is committed to the repo — cloning it gives everyone the right profile automatically.

3 Clone & Install

Clone the repo
bash
git clone https://github.com/YOUR_USERNAME/hostahtml.git
cd hostahtml
Install dependencies
bash
cd infra && npm install

This installs CDK, the AWS SDK, TypeScript, and esbuild (the bundler that packages your Lambda function).

Set your GitHub username in cdk.json

Open infra/cdk.json and replace REPLACE_WITH_YOUR_GITHUB_USERNAME with your actual GitHub username:

infra/cdk.json (edit this line)
"githubOwner": "your-github-username-here"

This scopes the GitHub Actions deployment role to your repo only — no-one else's pushes can trigger a deploy to your AWS account.

Understand the project layout
tree
infra/
  bin/hostahtml.ts         ← CDK entry point — creates the stack
  lib/hostahtml-stack.ts   ← Infrastructure definition (Lambda, API, S3, IAM)
  lambda/handler.ts        ← Your Lambda function code
  cdk.json                 ← CDK config: how to run the app, context variables
  tsconfig.json            ← TypeScript config
Azure equivalent

bin/hostahtml.ts = the Pulumi index.ts or the entry main.bicep — the top-level entry point that kicks off the deployment.

lib/hostahtml-stack.ts = the actual resource definitions, like a Bicep module or a Pulumi component.

cdk.json = Pulumi's Pulumi.yaml — it tells CDK how to run your TypeScript app and stores context variables (like your GitHub username).

4 Bootstrap CDK

Before CDK can deploy anything, it needs a one-time setup in your AWS account: an S3 bucket for deployment assets, an ECR repository for container images, and some IAM roles CDK uses internally. This is done once per AWS account + region.

Azure equivalent

This is like creating a Terraform/Pulumi state backend — a storage container where CDK can stash deployment artefacts and track stack state. Like terraform init, you run it once and then forget about it.

Get your account ID and region
bash
# Account ID (12 digits)
aws sts get-caller-identity --profile hostahtml --query Account --output text

# Region you configured
aws configure get region --profile hostahtml

Note both values down — you need them in the next step.

Run bootstrap

Replace 123456789012 with your account ID and eu-west-1 with your region:

bash
cd infra
cdk bootstrap aws://123456789012/eu-west-1 --profile hostahtml

Takes about 2 minutes. You'll see ✅ Environment aws://... when it's done. You never need to run this again for this account/region.

5 Google OAuth Setup

The frontend uses Google Sign-In to identify users. You need a Google OAuth 2.0 Client ID before deploying — it gets baked into both the Lambda (for token verification) and the frontend (for the sign-in button). This takes about 10 minutes on first time through.

ℹ️ What is a Google Cloud project? OAuth credentials live inside a Google Cloud project — Google's way of grouping resources and billing. You don't need to use any GCP services or pay anything; you just need a project as a container for the credentials. If your org already has a GCP project you can create credentials in, use that. Otherwise create a new free one.
Open Google Cloud Console and select or create a project

Go to console.cloud.google.com. Sign in with your work Google account.

In the top-left, next to the Google Cloud logo, you'll see a project name (or "Select a project"). Click it — a picker opens. If you see an existing project you can use, select it. Otherwise:

  1. Click New Project (top-right of the picker)
  2. Project name: hostahtml
  3. Organization: if you're logged in with a Google Workspace account you'll see your org here — leave it selected so the project lives under your org. If you want a personal project instead, select "No organization".
  4. Click Create and wait a few seconds for it to provision
  5. The project picker at the top should now show your new project — click it to switch to it if it isn't already selected
Configure the Google Auth Platform

In the left nav go to APIs & Services → OAuth consent screen. You'll land on a page that says "Google auth platform not configured yet" with a Get started button. Click it — this is a one-time initialisation step for the project.

A setup form appears. Fill it in:

  • App name: hostahtml
  • User support email: select your email from the dropdown

Next, choose an Audience:

  • Internal — only accounts in your Google Workspace org can sign in. No verification or publishing step needed. Use this if hostahtml is a company-internal tool.
  • External — any Google account can sign in. Requires a publishing step (see below). Use this if you want people outside your org to be able to sign in, or if you're using a personal Gmail.
💡 If you have a Workspace account, pick Internal It skips the publishing requirement entirely and naturally restricts access to your org. If you're not sure which org your account is in, check the domain of your email — if it's your company domain (not gmail.com), you're on Workspace and Internal will work.

Scroll down to Contact information and enter your email address. Agree to the terms and click Continue, then Create.

External only: publish the app If you chose External, you'll land on a dashboard showing Publishing status: Testing. In Testing mode only manually-added test users can sign in and tokens expire after 7 days. Click Publish App → Confirm to make it production. (Google won't manually review it just for Sign-In — verification is only required for sensitive scopes, which we don't use.)
Create an OAuth 2.0 Client ID

In the left nav go to APIs & Services → Credentials. Click + Create Credentials → OAuth client ID.

Fill in:

  • Application type: Web application
  • Name: hostahtml
  • Authorized JavaScript origins: click + Add URI and enter http://localhost:5173

Leave Authorized redirect URIs empty — Google Sign-In with Identity Services doesn't use redirects.

Click Create. A dialog appears showing your new credentials. The Client ID is the long string ending in .apps.googleusercontent.com. Copy it — you'll need it in the next step.

💡 The Client ID is not a secret. It will be visible in the compiled frontend JavaScript that anyone can read. That's fine — it's a public identifier, not a key. The security comes from the server-side token verification in Lambda, which confirms the token was issued for your specific Client ID.

If you close the dialog without copying, you can find the Client ID again under APIs & Services → Credentials — click the pencil icon next to your OAuth 2.0 Client ID.

Add the Client ID to .mise.toml and verify it loads

Open .mise.toml in the project root and add the Client ID under the [env] section:

toml
[env]
AWS_PROFILE = "hostahtml"
GOOGLE_CLIENT_ID = "YOUR_CLIENT_ID.apps.googleusercontent.com"

Replace YOUR_CLIENT_ID with the value you copied. Then trust the file and verify:

bash
mise trust
echo $GOOGLE_CLIENT_ID

You should see your Client ID printed. Since .mise.toml is committed to the repo, anyone who clones it gets both variables automatically after running mise trust once.

6 Deploy Manually

Your first deploy. CDK compiles your TypeScript, generates a CloudFormation template, and creates all your AWS resources in one command.

Run cdk deploy
bash
cd infra
cdk deploy --context googleClientId=$GOOGLE_CLIENT_ID --profile hostahtml

CDK shows you a list of resources it's about to create and asks for confirmation. Type y. The first deploy takes 5–10 minutes — CDK is compiling your Lambda, standing up API Gateway, S3, IAM, and a CloudFront distribution.

Azure equivalent

This is az deployment group create or pulumi up. CDK generates a CloudFormation template and submits it to AWS. CloudFormation is AWS's equivalent of ARM — it's the native resource provisioner, and CDK just writes it for you so you don't have to touch YAML.

Copy the stack outputs

When deploy finishes, CDK prints outputs. Copy them all — you'll use them in the next steps:

example output
Outputs:
HostahtmlStack.ApiUrl           = https://xxxxxxxxxx.execute-api.eu-west-1.amazonaws.com
HostahtmlStack.BucketName       = hostahtml-uploads-123456789012-eu-west-1
HostahtmlStack.FrontendBucketName = hostahtml-frontend-123456789012-eu-west-1
HostahtmlStack.FrontendUrl      = https://xxxxxxxxxxxx.cloudfront.net
HostahtmlStack.DistributionId   = EXXXXXXXXXX
HostahtmlStack.DeployRoleArn    = arn:aws:iam::123456789012:role/HostahtmlStack-...

FrontendUrl is your app's public URL. The frontend isn't deployed yet — that happens via GitHub Actions (Section 7). Keep this URL handy — you'll also add it to your Google OAuth authorized origins next.

Test the API

Replace the URL with your ApiUrl output:

bash
curl https://xxxxxxxxxx.execute-api.eu-west-1.amazonaws.com/

Expected response: {"status":"ok"}

Add the CloudFront URL to Google OAuth authorized origins

Go back to Google Cloud Console → APIs & Services → Credentials, click your OAuth 2.0 Client ID, and add your FrontendUrl output (e.g. https://xxxxxxxxxxxx.cloudfront.net) to Authorized JavaScript origins. Click Save.

Without this, the Google sign-in button will refuse to work on the deployed app.

Test the frontend locally

Start the Vite dev server to test Google Sign-In and upload before deploying:

bash
cd frontend
VITE_API_URL=https://YOUR_API_URL VITE_GOOGLE_CLIENT_ID=$GOOGLE_CLIENT_ID npm run dev

Open http://localhost:5173. Sign in with your Google account, then drag an HTML file onto the drop zone. You should get a pre-signed URL back — click it to confirm your page renders.

💡 Need a test file?
bash
echo "<h1>Hello from hostahtml!</h1>" > test.html

7 GitHub Actions CI/CD

🔐 OIDC — no stored secrets Instead of creating an IAM user and storing its access keys as GitHub secrets, we use OIDC (OpenID Connect). GitHub Actions proves its identity to AWS using a short-lived token tied to the specific repo and branch. AWS trusts it and issues temporary credentials. There are no long-lived secrets to leak or rotate. The CDK stack already set this up for you — you just need to tell GitHub the role ARN.
Azure equivalent

This is Workload Identity Federation in Azure — same concept. Rather than storing a service principal client secret in GitHub, you configure a trust relationship between GitHub Actions and Entra ID / AWS IAM. The platform exchanges a JWT for temporary credentials, scoped to the specific repo and branch.

Push the code to GitHub

Create a new repo on GitHub (private is fine), then:

bash
git remote add origin https://github.com/YOUR_USERNAME/hostahtml.git
git push -u origin main
Add three GitHub Actions secrets

In your GitHub repo go to Settings → Secrets and variables → Actions → New repository secret. Add:

  • AWS_DEPLOY_ROLE_ARN → the DeployRoleArn from your CDK outputs
  • AWS_REGION → eu-west-1 (or your region)
  • GOOGLE_CLIENT_ID → your Google OAuth Client ID (e.g. xxxxxx.apps.googleusercontent.com)

The deploy workflow uses these to: assume the AWS deploy role, set the region, and pass the Client ID to CDK (for the Lambda) and Vite (for the frontend build).

Push to main to trigger a deploy
bash
git commit --allow-empty -m "trigger deploy"
git push

Go to the Actions tab in your GitHub repo. Watch the Deploy workflow run. It will: deploy the CDK stack, build the Svelte frontend (injecting the API URL from stack outputs), sync the built files to S3, and invalidate the CloudFront cache. Expect about 5 minutes total.

8 Verify Everything

Hit the health check
bash
curl https://YOUR_API_URL/

Expected: {"status":"ok"}. If this still works after the GitHub Actions deploy, the CI/CD pipeline is deploying correctly.

Open the live frontend

After GitHub Actions finishes, your Svelte frontend should be live at the FrontendUrl from your CDK outputs (e.g. https://xxxxxxxxxxxx.cloudfront.net). Open it in a browser — you should see the hostahtml sign-in page.

Sign in with your Google account. Then drag an HTML file onto the drop zone — you should get a 7-day pre-signed link back. Click it to confirm the page renders.

Check CloudWatch Logs

In the AWS Console, go to CloudWatch → Log groups and find /aws/lambda/HostahtmlStack-ApiFunction.... You should see the upload logged there.

Azure equivalent

CloudWatch Logs = Application Insights / Azure Monitor. Lambda automatically ships its console.log output here. You can build dashboards, set up alerts, and query logs — all within CloudWatch.

Check S3 in the console

In the AWS Console, go to S3 and find your hostahtml-uploads-... bucket. You should see the files you uploaded.

Azure equivalent

S3 = Azure Blob Storage. S3 "buckets" = Blob Storage "containers". Objects inside are referenced by a "key" (file path within the bucket), not a URL path as in Azure.

🎉 You're live on AWS. You have a TypeScript Lambda behind API Gateway, a private S3 bucket with pre-signed URL access, and a GitHub Actions CI/CD pipeline — all running in an enterprise AWS account. Next step: add auth, file listing, deletion, and privacy controls to build out the full hostahtml app.
